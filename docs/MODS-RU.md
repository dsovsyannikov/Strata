## 2. Изменение 1 — дисковый кэш диалогов (`--conversation-cache-disk`)

**Проблема:** park/restore окна диалога держало снимок сессии целиком в RAM.

**Решение:** окно паркует/восстанавливает снимок потоком на диск — 128K-сессия паркуется ~0.3 с, занимает ~0.4 ГБ RAM вместо полной копии.

**Файлы:** `src/core/conversation_disk.cpp` (новый), `conversation_file.cpp`, `session.cpp`, `conversation_snapshot.cpp`, `program/generate.cpp` (опция). Отчёт: `strata-disk-cache-mod/` в workspace.

---

## 3. Изменение 2 — GDN-состояние в FP16 (`--gdn-f16`)

**Что:** рекуррентное состояние gated-delta-net (128×48×128 × 36 слоёв = 113.2 МБ → 56.6 МБ на последовательность) хранится как binary16; вся арифметика ядер остаётся F32 (элемент расширяется при чтении, сужается при записи).

**Результат:** файлы сессий −47.5%; чат-decode 10.8 → 11.9 ток/с (+10.2%) при 33W-клампе карты, +3% на полной мощности; F32-путь компилируется в строго прежние биты (дефолт не меняется). Конвертер проверен на сублималах/NaN/Inf; restore конвертирует на лету.

**Файлы:** `include/strata/kernels/gdn_state.hpp` + `src/kernels/gdn_state.cpp` + `gdn_state_io.cuh` (новые), шаблонизация GDN-ядер `<ST>`: `gdn.cu`, `native_gdn.cu`, `fused_gdn.cu`, `verify_kernels.cu`, `prefill/kernels.cu`; `session.cpp`, `conversation_state.cpp`, `generate.cpp`.

## 4. Изменение 3 — NVFP4 KV-кэш (`--kv nvfp4`)

**Формат:** 4-битные E2M1-коды + один 8-битный E4M3-скейл на группу из 16, после того же Walsh-Hadamard-вращения, что у `--kv q4_0`. 144 Б на ячейку/голову → 576 Б на ячейку против 1056 у INT8; **6 912 Б/токен (−45.5%)**, на 128K-контексте 0.88 ГБ против 1.62. Семантика квантования — NInfer (`amax/6`, RN-деление, clamp [2⁻⁹, 448]).

**Чтение (v1, режим 5):** удвоенные величины E2M1 {0,.5,1,1.5,2,3,4,6}×2 — точные INT8-коды → FP16-тензорные ядра через LUT; скейл E4M3 (ополовиненный для удвоенных кодов) применяется в F32.

**Файлы:** `nvfp4_codec.hpp` (новый, host+device одинаковые строки), `kv_nf4.hpp` / `kv_nf4.cu` (новые), `qsa_decode_attn.cu`, `kv_stream.cu` (kKvNvfp4), `layer.cpp`, `prefill.cpp`, `verify.cpp`, `mtp.cpp`, `conversation_snapshot.cpp`, `generate.cpp`; паритет-тест `kv_nf4_parity.cpp` (12 проверок).

**Качество:** needle 16K 3/3 = INT8; факт-батарея чистая; стриминг с `--kv-resident` работает.

> ⚠ Слоты/сессии на диске, записанные до смены порядка ниблов (см. §5), невалидны — старые nvfp4-файлы в `Strata-data/sessions` удалить.

## 5. Изменение 4 — нативный FP4-тензорный путь (режим 6) и фикс стриминга

### 5.1 Порядок ниблов → MMA-совместимый

Кодек пакует **смежные пары** (байт m = элементы 2m/2m+1) вместо сплита (j, j+8) — пул K становится готовым B-операндом MMA без репака (NInfer сама использует парный порядок в MMA-путях, сплит — только в кэше). Обновлены все читатели: `kv_nf4.cu`, `qsa_decode_attn.cu`, режим 5.

### 5.2 Q·Kᵀ на `mxf4nvf4` (sm_120a)

Инструкция: `mma.sync.kind::mxf4nvf4.block_scale.scale_vec::4X.m16n8k64.row.col.f32.e2m1.e2m1.f32.ue4m3` (обёртка NInfer дословно). Ключевое: **K-пул — готовый B-операнд**: кодовые байты читаются тремя u32 из cp.async-стейджа, 16 байт E4M3 — готовые слова SFB. Q квантуется на лету в hi-половину + lo-остаток (трюк fp16-ядер в 4 битах); фрагменты A — в регистрах на всё ядро. P·V остаётся точным FP16-путём: скейлы V меняются per-cell, ось k MMA их не выражает (vLLM отказался от FP4 P·V по той же причине).

Инженерные детали: cp.async двойная буферизация; `"memory"`-клобберы на asm-обёртках cp.async (без них компилятор переставляет smem-чтения через `wait_group` — гонка); пустая commit-группа в хвосте конвейера (wait1 должен видеть две группы); LUT в shared (в local — 96 Б стека и 11× медленнее цикл). Отключение: `STRATA_PROMPT_ATTN_NF4=0` (режим 5). Опция `STRATA_NF4_PV8=1/2` — P в E4M3 × V в E2M1 на `kind::f8f6f4` (контейнер e2m1 = биты [5:2] байта): верифицировано EXACT, измерено в ноль с FP16-путём (сборка A-фрагментов съедает выигрыш MMA) — оставлено как опция.

### 5.3 Фикс «гона» стриминга (главный баг-фикс)

**Симптом:** illegal access при контексте > `--kv-resident`, всплывал в verify через 1–2 слоя («layer 3»…«mtp draft»), выглядел как гон.

**Причина:** v1-аппенды nvfp4 писали девайс-пулы по **логической** строке `(pos/page)·heads`, а не по **слот-строке** `page·heads` (у q4 — правильные две строки: слот для пулов, логика для host-копии). При identity-таблице (резидент) строки совпадают; на кольце драфтера / стриминге — выход за границы пула.

**Фикс:** слот-строка для пулов, логическая для host-копии, как у q4 + **тест с перемешанной таблицей** в `kv_nf4_parity` (слот- и логическая строки больше никогда молча не совпадут). После фикса: needle 32K на дефолт-конфиге (стриминг + кольцо + режим 6) — **3/3 FOUND**; ранее тот же прогон падал 7/7.

### 5.4 Числа (RTX 5090 Laptop, полная мощность)

Ядро prompt-внимания (32K ctx / 2048 запроса, меньше = лучше):

| Путь | мс |
|---|---|
| FP32 decode (старый путь) | 78–119 |
| nvfp4, режим 5 (FP16 MMA) | 13.6 |
| **nvfp4, режим 6 (натив. FP4)** | **6.9–7.2** |
| int8 (эталон) | 5.5 |

Движок (равные конфиги, интерлив): prefill 14K/32K ток/с: fork-nvfp4-m6 **1973/2164**; fork-nvfp4-m5 1825/1940 (нативный FP4 даёт **+7–8% к режиму 5**); int8 2065/2197; оригинал-fp16 1827/1946. Против дефолта оригинала **+8–11%**, с int8 — паритет.

## 6. Изменение 5 — сборка без потери скорости + честная статистика

### 6.1 Обязательные флаги

```
cmake -S . -B build -G Ninja \
  -DSTRATA_ENABLE_CUDA=ON -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_CUDA_ARCHITECTURES=120a \
  -DSTRATA_PORTABLE=ON \
  -DCMAKE_CUDA_COMPILER=<nvcc> -DCUDAToolkit_ROOT=<toolkit> -DSTRATA_GGML_DIR=<llama.cpp>
```

- **`120a`**: инструкции `mxf4nvf4`/`f8f6f4` существуют только в arch-specific цели; CMake определяет `STRATA_CUDA_ARCH_SPECIFIC`, рантайм не запустит ядра из plain-sm_120.
- **`STRATA_PORTABLE=ON`**: на тулчейнах, где нативная детекция ggml не работает (наш «fakevs»), без флага ggml-CPU собирается **вовсе без SIMD** → decode −20% (62–66 против 74–84 ток/с). С флагом decode форка = паритет с релизным движком оригинала (74.4 против 74.6–77.1, медианы интерлив-прогонов).

### 6.2 Статистика стриминга

Формула лога «MiB read from RAM» была захардкожена `miss × 4224` (блок int8) и завышала трафик nvfp4 в 1.83×. Теперь — размер блока собственного формата состояния (`core::qsa_kv_format` → `kv_block_bytes`).

## 7. Память VRAM: эксперты и стриминг (замерено на живых движках)

Эксперт-кэш (слоты; дефолт-конфиг `--kv-resident 32768`, max-context 262144):

| Конфигурация | KV в VRAM | Слотов |
|---|---|---|
| int8, resident 32768 (= ваш текущий) | 0.4 ГБ + стриминг | 9 960 |
| **int8, всё в VRAM (дефолт без флага)** | 3.32 ГБ | 8 150 (−1 810) |
| nvfp4, resident 32768 | 0.2 ГБ + стриминг | **10 077** (+117) |
| **nvfp4, всё в VRAM** | 1.81 ГБ | **9 079** (−998) |

- Форк на int8 = бит-в-бит те же 9 960 слотов, что main (мод ничего не отнимает).
- `--kv-resident` пишет инсталлятор (setup.py): при контексте ≥64K и достатке RAM — «KV живёт в RAM, больше экспертов в VRAM».
- nvfp4 делает полную резидентность дешёвой (−998 слотов вместо −1 810) и режет трафик стриминга вдвое.

Трафик стриминга (счётчики движка, одинаковые needle-сессии; промахи идентичны — 43 140 и 86 280 чтений, 69.5%/84.4% попаданий):

| | int8 | nvfp4 |
|---|---|---|
| байт на промах блока | 4 224 | **2 304 (−45%)** |
| реально прочитано из RAM | ~52.8 MiB | **~28.7 MiB** |

## 8. Гейты качества (все зелёные)

- `qsa_prompt_attn_parity` — 0 FAIL (все форматы; для nvfp4 FP64-референс с квантованным Q: ядро = своя семантика на 2·10⁻⁶; шум Q-FP4 ~2.4% шкалы на синтетике).
- `kv_nf4_parity` — OK (12 проверок + ring-table тест слот-строк).
- Микротесты инструкций: `nf4_mma_probe` EXACT; `f8f6f4_probe` EXACT (включая конструкцию P·V против CPU-эмуляции); `f8f6f4_discovery` — one-hot определение раскладок.
- Движок: needle 32K depths 10/50/90 — **3/3 FOUND** (дефолт-конфиг, стриминг + кольцо + режим 6); факт-батарея чистая; decode/_prefill — таблицы выше.

## 9. Известные ограничения

- Park/restore конверсационного кэша под nvfp4 не бит-точен (restored-continuation дрейфует; slot save/restore бит-точен; на качество needle не влияет; унаследовано с v1).
- PV-f8f6f4 выигрыша не даёт (опция для экспериментов).
- Старые nvfp4-слоты на диске (до смены ниблов) невалидны.
- Bench-разброс ±5% от клоков/термals: сравнивать только парные интерлив-прогоны (скрипты так и делают).
